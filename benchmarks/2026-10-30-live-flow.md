# Live invite flow with Meta working (Render free plan, Virginia)

Measured 2026-10-30 against https://strollcall.onrender.com at commit 21eaf89. The Meta Model API answered from
the server (free credits). Script: A's text is parsed (`/api/intents/parse`), A creates the invite, B accepts,
then A polls every 0.25 s until the plan is shown. Start points are two public places, Union Square Park and
the Washington Square Arch. A: "about 25 minutes, quiet streets, coffee at the end". B: "I'd like to pass a
park, not too long". Up to six options per plan.

| Run | A's wish read (s) | A creates invite (s) | B accepts -> plan shown (s) | Sources not "meta" |
|---|---|---|---|---|
| 1 | 10.72 | 5.72 | 11.93 | negotiation, ranking (rule-based) |
| 2 | 6.25 | 4.49 | 10.97 | none |
| 3 | 6.41 | 4.82 | 12.51 | none |
| **Median** | **6.41** | **4.82** | **11.93** | |

All three runs gave six options. Routing and places are local by design (`local`, `snapshot`). The invite
picture is Muse Image, made ahead of time.

Server stage timings, median of the three runs (s): B's wish read 4.42, wishes 2.25 (in parallel with B's wish),
balancing (negotiation) 2.59, planning 0.01-0.43, ranking 3.89. With Meta answering, the Muse Spark steps take
almost all of the time; planning itself takes well under a second. The earlier figure of 1-2 s per step
(2026-10-28) no longer holds: steps take 2-5 s each, even at `minimal` reasoning effort.

Why run 1 shows rule-based parts: Muse Spark's answer was received, then rejected by the honesty checks.
- Negotiation: the text called something "quiet". Our data cannot confirm quiet, so it is allowed only when
  worded as someone's wish.
- Ranking: one reason used the word "bakery" for an option whose places do not support it. From this commit on,
  the log records the rejected reason's text.

Before the fix in 21eaf89, three earlier runs the same day had ranking rejected every time. The checker read
other options' names ("Dominique Ansel Bakery", "5th Ave & E 12th St") as claims about the option being
explained. Those runs took 4.74 / 7.71 / 14.47 s to read A's wish, 4.52-5.23 s to create the invite, and
11.67 / 12.70 / 13.66 s from accept to plan.

Voice: one WAV recording (4.4 s, 16 kHz mono, synthesized speech) sent to `/api/voice/transcribe` came back
from Muse Voice Transcribe as "I would like a quiet walk about 25 minutes and coffee at the end..". It took
about 2.2 s and was labelled `meta`.

All steps were labelled `meta` in all three runs, with six options each.

- **Plan shown vs explained:** the plan appears about 7 s before the explanation (median 9.6 s vs 16.5 s), so
  people see their walk sooner.
- **Meta was slower than in the morning runs:** ranking took 5.3-6.7 s (morning median 3.9 s) and B's wish
  4.9-9.3 s at minimal effort. Absolute times vary a lot with Meta's load; compare within a run, not across.
- **Reading A's wish:**
  - Before, `/api/intents/parse` ran at the default `low` effort with a 4096-token output cap.
  - It now runs at `minimal`. The server logs show 351-1245 output tokens per parse, all `finish=stop`, under the
    new 1536 cap.
  - Locally, on three wishes measured back to back: `low` 6.7 s median (1396-2073 output tokens); `minimal` 3.0 s
    (561-884), with the same parsed intents.
  - Live, the median went from 6.41 s to 5.42 s (3.77-9.73 s), within Meta's run-to-run spread.
- **Creating the invite (8 s median):** almost all of it is the Muse Spark invite line. That call still runs at
  `low` effort with the full cap. It was not part of this change.

## After: no parse for an empty wish, B's wish read while typing (commit d318f85)

2026-10-30 ~14:40 ET. Script: same start points and A's text; each run is a new invite. In the "with a wish"
runs the script does what the page does after B stops typing: it sends B's text to `/api/intents/parse`
without waiting for the answer, waits 3 s (B sets a start point and taps "I'm in"), then accepts. B's texts:
"I'd like to pass a park, not too long", "somewhere green would be nice, I'm bringing my dog", "not too far
please, maybe a bakery at the end".

| B's wish | Run | Accept -> plan shown (s) | Accept -> explained (s) | B's wish read after accept (s) |
|---|---|---|---|---|
| empty | 1 | 3.62 | 6.36 | – (skipped) |
| empty | 2 | 2.80 | 7.14 | – |
| empty | 3 | 1.42 | 5.65 | – |
| **empty, median** | | **2.80** | **6.36** | |
| typed | 1 | 3.74 | 10.97 | 0.74 (pre-parse still finishing) |
| typed | 2 | 6.50 | 9.62 | 3.68 (pre-parse still running at accept) |
| typed | 3 | 3.00 | 7.60 | 0.00 (ready) |
| **typed, median** | | **3.74** | **9.62** | |

Before this change, accept to plan shown took 8.65 s (median, earlier run today). Every step in all six runs was
labelled `meta`, and every plan had six options.

- **Empty wish:** nothing waits on Meta before planning except reading A's wishes (1.1-2.8 s). There is no
  negotiation and no tradeoff line.
- **Typed wish:** a parse that is still running when B taps is shared, not repeated (runs 1-2), so tapping early
  only waits for the rest of it. Negotiation (2.4-2.7 s) now runs alongside reading the wishes.
- **The explanation still arrives afterwards:** ranking took 2.8-7.2 s, so the explanation follows 3-7 s after the
  plan.
